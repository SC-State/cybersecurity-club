Portfolio basics

Write your project README

Every runbook ends by pushing a write-up to GitHub. That write-up — the README — is the thing a recruiter actually reads. A great project with a one-line README looks like nothing; a simple project with a clear README looks like you know what you're doing. Here's how to write one that lands, in about ten minutes.

Start here

What a good README has

Five short parts. That's it. You're not writing an essay — you're showing a recruiter you did real work and understood it.

  • A title and one-line summary — what the project is.
  • What I did — a few bullets of what you accomplished.
  • How I did it — the key steps, commands, or config (in code blocks).
  • What I learned — one or two honest takeaways. This is what interviewers probe.
  • A screenshot or two — proof it actually ran.
The golden rule: keep it real and keep it safe. No real passwords, keys, or anything from a system you don't own — and blur personal details out of screenshots. More on that at the bottom.
Markdown in 60 seconds

How to format it

A README is a README.md file written in Markdown — plain text with a few symbols that GitHub turns into formatting. You only need these:

Big heading

**bold text**

- a bullet

inline code

A block of code or commands — wrap it in three backticks on their own lines:

```

```

The template

Paste this into your README.md, then fill in the brackets with your own project. Delete any part that doesn't apply.

# [Project name]

[One sentence: what this project is.]

## What I did
- [What you built or accomplished]
- [Another thing, if there is one]

## How I did it
[A short walkthrough. Paste the key commands or config in a code block:]

```
[your commands here]
```

## What I learned
- [One real takeaway]
- [What you would do differently, or what surprised you]

Example

A real one, filled in

Here's the same template filled out for the Build a cybersecurity home lab runbook. Short, clear, and it reads like someone who did the work.

# Cybersecurity Home Lab

An isolated virtual lab for safely practicing offensive and
defensive security, built with VirtualBox.

## What I did
- Set up VirtualBox with Kali Linux and a vulnerable target VM
- Put both machines on a host-only network so they can reach
  each other but not the internet
- Used snapshots so I can break things and roll back instantly

## How I did it
Both VMs run on a private host-only network (192.168.56.0/24).
I confirmed they could see each other by pinging the target
from Kali:

```
ping -c 4 192.168.56.101
```

## What I learned
- Why you isolate a lab: a host-only network means nothing I do
  can reach my real network or the internet by accident.
- Snapshots are not backups — they live in the same VM file,
  so I keep the original download too.

## Screenshots
![successful ping between Kali and the target](ping-success.png)
That's it. Notice it names the real network, shows one real command, and the "what I learned" lines sound like a person who understood it — not a tutorial. That's what makes it résumé-worthy.
Stay safe

Screenshots & privacy

A screenshot is great proof — but it can leak things you don't want public. Two steps:

1 — Take the screenshot

  • Windows: press Win + Shift + S, drag over the area, and it's copied — paste it into Paint and save as a .png.
  • Mac: press Cmd + Shift + 4, drag over the area, and it saves to your Desktop.

2 — Blur anything personal first

  • Real IP addresses you don't own, hostnames, account names, email addresses, and anything that identifies you or a real system.
  • Open the image in any editor (Paint, Preview, Photos) and draw a solid box over it, or crop it out. A black rectangle is fine.
Never commit: real passwords, API keys, private keys, raw log files, .pcap captures, or .eml email files. Publish screenshots of the harmless part you're explaining, not the raw evidence.
Now push it up

Got your README written? Put it on GitHub with the push guide, then paste your repo link in the GroupMe. That's a finished, recruiter-ready project.
